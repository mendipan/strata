# Drift and regression: focused test/design plan

Checkpoint note, 2026-10-04: Historical design input. The subsequent [bounded hardening result](DRIFT_REGRESSION_HARDENING.md) records actual D1-D6 fixture evidence; [S2](MEDIATION_SLICE2.md) adds versioned selection/Release and deliberate v0.2 evolution. Original instructions and proposed checks below describe the planning pass. Their execution status follows the linked results; general drift-prevention and comparative claims remain unproven.

This design matrix explains the bounded drift/regression cases. The implemented checker-bound profile work is described in [hardening](DRIFT_REGRESSION_HARDENING.md); remaining cases are proposals, not current behavior. Use the existing node:test suite, profile runner and authorization paths.

**Recommendation:** add a small cross-release adversarial test increment. Existing tests establish useful exact-reference, evidence and authorization gates, but do not establish preservation of a repaired behavior across later materialization, or prevent all forms of weakened-test coverage. Do not claim drift reduction as a measured outcome yet.

## 1. What counts as drift or regression

| Outcome | Meaning and treatment |
| --- | --- |
| Textual drift | Wording, description or formatting changes. Map-key/set reordering already normalizes; ordinary strings remain exact. Different prose is neither proof of changed behavior nor proof of equivalence. Current exact binding conservatively invalidates changed content; unexplained contradictions require review. |
| Intended behavior evolution | An explicitly authored, exactly authorized change to the prior contract, with fresh evidence for the resulting candidate. A 900-to-1,200-second expiry change can be correct. Preserve unaffected obligations; retire only the explicitly superseded expectation. |
| Intent loss or unauthorized weakening | A requirement/criterion disappears or changes without the required authored change and authorization, or a linked test stops checking the obligation it purports to cover. Reject known structural/coverage violations; route ambiguous changes to the responsible human. |
| Actual implementation regression | New output violates a still-active, previously satisfied obligation: for example, a hold remains active at its required expiry. Detect by executing that output against an independently retained expectation. Correct hashes and a coherent changed specification cannot establish behavioral correctness. |

A semantic diff locates changes; it cannot decide whether a new product requirement is desirable. A regression relative to a task's intended outcome can coexist with perfect implementation of a mistakenly approved requirement. Preserve this distinction in results.

## 3. Specific gaps found in this pass

These are source-grounded findings and proposed falsifiers, not executed exploit or regression results.

**G1 — Coverage edges need semantic checking, not just existing endpoints (P0).** [model.ts](../src/model.ts), `checkTree`, checks that referenced criteria and their subjects exist. [profile.ts](../src/profile.ts), `knownRequirement` and `materialize`, recognizes requirements and each criterion's allowed subjects separately; it does not require a criterion linked by an obligation to name that obligation or perform its required check. A concrete candidate can replace `booking.hold/acceptance.exclusive` with `booking.lifecycle`, fixture `exclusive`, subjects `[booking.hold/requirements.expiry]`, and the matching recognized statement. The unchanged exclusivity requirement and occupied-failure contract still link to the key `exclusive`, but the generated coverage now points to lifecycle checking. This is a coverage hole, not evidence that the current template actually permits double booking.

The guardian loop in [core.ts](../src/core.ts), `release`, compares the protected requirement value; changing only its linked criterion does not trigger that item-change check. Scope/release approval still applies. Minimum response: enforce subject/required-check compatibility for the bounded profile and expose linked-criterion changes in existing review. A valid alternative check may require human review; a check of an unrelated subject must fail materialization. Do not silently invent a new general guardian inheritance rule. S1's nonempty acceptance minimum fixes a separate known v0.1 gap, not G1.

**G2 — The runtime oracle shares the generated configuration (P0).** [runner.ts](../src/runner.ts), `runFixtureEvidence`, imports both `createBooking` and `config` from the generated module and calculates timing expectations from that `config`. If an authorized new materializer incorrectly emits 600 seconds for retained 900-second intent, internally consistent output can satisfy those relative assertions. Registration prevents arbitrary substituted bytes under today's correct template; it does not prove a future pinned template correct. Minimum response: drive assertions from independently reviewed semantic expectations, retain literal cross-release boundary cases, and compare output configuration to the intended snapshot as an additional check.

**G3 — Check labels do not pin checker implementation/fixture content (P0 design, integrate with versioning).** `profileFingerprint` hashes `PROFILE` and `PROGRAM`; evidence carries check/version/fixture strings and a fixed executor label. It does not content-bind `runner.ts`'s check bodies or a separately measured fixture/oracle artifact. The runner selects functions by check ID; fixture names do not select independent input bytes. Editing a check while retaining its version can therefore leave existing evidence bindings unchanged. Minimum response: bind a reviewed checker/fixture digest into the existing versioned profile/evidence contract and use the host-owned runner to enforce it. Keep legacy evidence explicitly legacy; do not reinterpret old immutable identities. Final shape belongs with the profile/version dispatch contract, without casually changing a frozen model schema.

**G4 — Reports do not yet survive candidate renaming (P1, already assigned).** `Engine.evaluate` selects interaction reports by exact Composition ID/revision. The accepted S2 design already specifies project-level report carry-forward, exact dispositions and generation rechecks. Add the regression below to S2; do not create a second report lifecycle implementation.

The absence of an independent full inheritance assertion is a **test gap**, not an observed drop in today's flattening code. General prose equivalence, undeclared-dependency discovery and reviewer correctness are architectural limits; this pass proposes no general semantic oracle.

## 4. One small cross-release fixture

Reuse the four booking Blocks and existing authors/selector/release fixtures. Use injected logical time and fresh local output/state directories. `R1`, `R2`, `R3` below are test aliases for actual immutable Release refs, not caller-chosen Release identities.

| Stage | Fixed intent and expected behavior |
| --- | --- |
| Bootstrap | Existing `R0@1`: 600-second holds, exclusive resource, reminders off. |
| R1: retained repair | Existing approved demo selection yields 900 seconds, one reminder 60 seconds before expiry, exclusivity, lifecycle and `layer-reminder` acceptance. Before accepting the corrected output, demonstrate that a synthetic old expiry defect fails. The defect is `now > expires` instead of `now >= expires`; it is a **test-seeded bug**, not a claim about repository bug history. |
| R2: later maintenance | Start from R1 as a complete baseline in a fresh Engine, without replaying old Layers. A new owned Layer adds only a standalone `booking.lifecycle` criterion, key `drift-lifecycle`, distinct fixture name, subject `booking.hold/requirements.expiry`. Re-materialize and obtain fresh evidence. All existing behavior and obligations survive. Also evaluate an empty-selection child of R1. |
| R3: authorized evolution | From R2, explicitly change the complete expiry requirement from 900 to 1,200 seconds. Keep the 60-second reminder lead and exclusivity. Review the consumer impact and exact change; obtain fresh evidence and exact responsible-scope/release approvals. Expected reminder is now 1,140 seconds and expiry is 1,200. Selection approval alone is insufficient. |

Keep a small **test-owned expected item/value map** in the existing fixture/helper lane, reviewed independently of the candidate. It is test data, not a new semantic record type. Enumerate requirement, acceptance, contract, relationship and purpose keys directly; do not compute expected coverage with `core.obligations` or copy it from the realization. R1 has 21 such obligations and 10 acceptance items; R2 adds one, yielding 22 and 11. Counts are secondary to exact keys, values, acceptance links and provenance. An empty-selection child preserves R1's complete map. For R3, change only the explicitly approved expiry record in the expected map.

Representative boundary assertions, repeated against R1 and R2 output:

```text
hold(room, a) -> accepted, expires = 900
hold(room, b) -> rejected; exactly one hold remains
advance(839) -> zero reminders
advance(1)   -> one reminder at 840
advance(0)   -> still one reminder
advance(59)  -> one active hold at 899
advance(1)   -> zero active holds at 900
hold(room, b) -> accepted
```

Values come from the reviewed fixture, never `module.config`. For R3, exercise 900 as a still-active boundary, 1,139/1,140 for reminders and 1,199/1,200 for expiry. The old *900-second expiry* expectation is deliberately superseded; exclusivity and at-most-once obligations remain. Keep old artifacts/evidence for historical inspection rather than deleting the old failing check wholesale.

S1 asset variant: use its fresh isolated v0.2 bootstrap and pinned retain-only profile, not an implicit migration of R1. Attach one valid local background PNG, then revise the pin to another valid image. Generated executable bytes may remain identical while candidate/asset closure changes. S1 must continue to reject v0.2 Release as unsupported until S2 gates exist. An unsupported result is a capability-boundary pass, not a successful cross-release asset test.

## 6. Integration, success measures and trust limits

Implement D1-D6 in the existing core/CLI tests with the smallest shared fixture helpers; G1/G2 come first. Attach D4's assets and D7 to the already assigned S1 cases; attach D8 and mediated authorization checks to S2. Reuse security tests for caller restrictions. A focused Node end-to-end path is sufficient for application behavior; use the existing broker matrix only where a changed shared-service/publication boundary needs verification. No new stress campaign or duplicate test framework.

For every injected defect retain: test ID, exact baseline/Layer/candidate/profile/checker/fixture/output hashes, expected active obligations, actual observations, rejection stage/code, publication-index delta, and whether the seed was reached. Separate mechanical observations, synthetic role attestations and actual human judgment. Proposed codes for new coverage/digest gates must be frozen by the owner; this plan invents no implemented error names.

Completion requires:

- Every applicable D1-D6 case passes on the corrected implementation; its paired valid control also reaches its intended successful boundary. R1/R2 and authorized R3 actually publish and run where the capability is enabled. An always-blocking implementation fails this requirement.
- **Zero false acceptances among the enumerated unsafe cases**, with all named unsafe seeds detected at their intended gate or independent assertion. Report `detected / attempted / inconclusive / deferred` for each mutation class. Unknown-profile rejection, skipped tests, or crashes before the target assertion do not count as behavioral detection.
- **Zero unexplained obligation losses**: exact expected IDs/values/links/provenance match across Releases, with approved changes listed explicitly. Do not report only “100% coverage” from candidate-derived denominators.
- **All stale-evidence substitutions rejected**, paired with fresh-evidence success where supported. Count asset and S2 cases separately while their capabilities are pending; do not omit them from the report or label them passing.
- **No unnecessary rejection of the declared valid controls**, including pinned-old-peer selection and authorized evolution. Conservative prose/asset revalidation and required human decisions are recorded costs, not automatically false positives.

These are deterministic acceptance criteria for a finite fixture, not statistical estimates of reliability. They establish neither zero bugs nor superiority to another development workflow.

The trusted oracle here is a reviewed, test-owned expected behavior/item map, an independently maintained checker, the trusted local host and measured output. Independence means the author/materializer cannot quietly edit expectations in the same proposal; it does not mean the checker is infallible. Avoid deriving expected outputs from generated code or letting the same changed requirement automatically rewrite all regression expectations. Review an intended expectation change against the exact authorized change, retaining unaffected checks. Pin checker/input identities; hashes establish identity, not correctness or authorship.

A second model agreeing, a separately named fixture reviewer, or two checks sharing the same faulty assumptions is not independent proof. The local host/operator can alter fixtures, checks and records; imported passing evidence still depends on that trusted boundary. Tests miss unmodeled inputs, undeclared interactions and wrong-but-approved intent. Human review is needed for requirement meaning, impact and permitted weakening; deterministic gates must still reject known invalid records, failed checks, stale bindings and absent authority.

No comparative experiment is needed to implement this increment. If later requested, extend the already proposed [concurrency research](AGENT_CONCURRENCY_RESEARCH.md), sections 7 and 9, rather than creating another benchmark plan. Pair the same repair/later-maintenance/evolution tasks across its competent Git, intent-in-Git and Strata arms. Keep the model/version/reasoning, underlying task facts, supported generator, host isolation, budgets and approval policy equivalent; predeclare held-out regression checks and randomized/repeated runs. Count accepted correct maintenance tasks, introduced/reintroduced defects, lost obligations and human review/repair effort; include failures, unsupported cases and total model work. A template-only Strata run cannot establish better model development than open-ended coding elsewhere.

**Any model-backed run remains proposed and approval-gated.** Before execution, provide exact model/provider, data scope, call/token/attempt/time limits, total enforceable cost cap, run count and outputs for explicit approval. Existing account access, this document and an accepted semantic decision supply none of that authorization. No model call, benchmark or paid test is part of this handoff.

Use these claims after the corresponding evidence exists:

- Now: “Strata's local prototype enforces exact context, evidence and approval gates. Cross-release regression protection and behavioral coverage have additional identified gaps.”
- After this suite: “For the named booking fixtures, the checks detected the seeded regressions and stale substitutions, preserved specified inherited obligations, and accepted explicitly authorized evolution with fresh evidence.” Include actual counts and deferred cases.
- Still unproven: “Strata reduces agent-induced regressions or drift compared with a competent alternative workflow.” Do not say “prevents regressions,” “tests prove no bugs,” or equate an approved Release with proof of arbitrary intent correctness.

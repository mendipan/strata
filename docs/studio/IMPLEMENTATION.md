## Synthetic acceptance fixtures

Use a new generic synthetic project with a root and two child Blocks, an explicitly declared relationship and criteria; one alternate proposal conflicts on a single atomic requirement and one dependent proposal has an exact read/dependency and final-value assumption. A prepared source proposal has unresolved questions and observed/inferred/correction/uncovered traces. Use repository-created synthetic source files only.

For generic authoring/preview assertions, the profile may correctly be unavailable. For successful realization/evidence/Release acceptance, reuse an existing bounded counter/booking fixture and its measured runner/independent oracle. Do not relabel fabricated JSON results as a run, add an always-pass profile, or copy an external application's intent/source into tests. Test v0.1 and activated v0.2 separately; public fixture identities remain test identities.

## Validation sequence and stop conditions

Use the repository's installed tooling; no deployment or cloud calls. Start with `npm run typecheck`, `npm run build`, targeted new tests and the touched existing suites (`cli`, `content-cli`, `security`, `recovery`, `explorer-*`, `mediation-*`, `profile-separation`). Use `tests/no-external-fetch.mjs` for offline fixture execution. Run the broader required local suite after integration; use the repository's existing browser harness/Playwright installation for screenshots and input tests. Do not claim browser/manual or SDK tests passed unless actually run.

Check schema generation and link verification when schema/docs change. Tests must exercise stale/retry/crash paths through the persistence boundary, not only mocked button states. Store browser screenshots and synthetic run receipts in temporary output, not private payloads or live state. No need to run application suites for this docs-only planning commit; validate paths, links, diff scope and commit isolation.

Block deployment or live write activation until their separate authorized configuration exists. B/C are the first deliverable, not the end of persistent Studio authoring: D and H2/H3 have explicit model/security/test gates and complete the requested capability. Chat, external identity providers, active authority migration, automatic source inference and arbitrary application generation are not implicit follow-ups. If a later engine or visual decision materially departs from this plan, return it to Astra High for review before coding it.

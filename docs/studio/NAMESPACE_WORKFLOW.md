# Persistent Artifacts namespace workflow

This opt-in Studio host mode implements one owner-approved **development** namespace with authorization lasting until revoked. It uses the protected owner credential store, finite owner/actor sessions, the existing Strata broker, and real Artifacts REST and Git protocol adapters. Local tests inject a strict synthetic provider; they do not establish live provider conformance or authorize activation.

## Working slice

1. The operator installs an exact namespace policy and a new private catalog lineage. The owner signs in, saves the Artifacts API token in Settings, and approves the displayed account, namespace, permissions and creation-token policy.
2. The top-bar repository switcher lists registered projects immediately. **Discover repositories** performs an explicit bounded provider list/search request, with cursor pagination. Settings remains connection administration. Existing non-namespace host modes retain their navigation.
3. **Create Strata project** creates a repository in the already-existing namespace, initializes an authenticated v0.3 Block project, and saves a genuine immutable bootstrap baseline through the broker and Git adapter. The baseline is labelled **no validation evidence**.
4. Open a registered project, inspect its Blocks, and save or revise owned Layer drafts. Switching changes the exact repository/project binding, clears actor authority and stale views, and retains each project's private writer state. Restart and ordinary sign-in retain namespace consent, selected project, drafts and spent allowance.
5. Pause/resume is reversible. Revoke writes a permanent tombstone for this lineage. Neither operation deletes repositories, resets spending or changes historical Strata records.

Namespace approval alone grants discover/create/read/draft capability. The optional, explicitly confirmed [first-project contract](FIRST_PROJECT.md) provisions a supported collection baseline and bounded-lifetime authority for one named human to author, review, validate and approve Releases. It measures the exact finite output through the existing Node checker. This is a single-person workflow; existing content publication, evidence and Release gates remain enforced. Without that contract, initialization remains an empty draft-only project. Agent execution requires separate consent.

## Authority and state

- `namespace-policy.ts` seals owner, installation, account, namespace, lifetime, permissions, author identity, project capacity, provider contract and allowance. Policy edits cannot silently rebind retained state.
- `namespace-store.ts` retains catalog, operation outcomes, monotonic reservations and a revocation tombstone. A service lease excludes a second writer. Missing, inconsistent or stale leased state needs operator reconciliation; startup never reconstructs a missing catalog or budget. The normal 2,048-entry history reserves two additional entries for pause then revoke, or one for direct revoke. Full-history pause is durable; resume and other ordinary work stay unavailable until separately reviewed operator reconciliation. Prior outcomes and spending are never truncated to make room. An older binary that cannot parse these reserved entries must not be used as a rollback path.
- `namespace-manager.ts` uses CAS revisions, immutable request IDs and one active discover/select/create action. Pause, logout, credential changes and revoke invalidate in-flight leases. Control changes retain their original owner/session and control generation through queued admission and final publication: private files are prepared and flushed, authority and privileged freshness are checked again, then synchronous publication leaves no event-loop gap. Control state and its completed receipt publish together. Logout after that commit preserves legitimate durable consent. A creation is durably marked uncertain before its provider POST. Interrupted pre-dispatch actions are closed on startup; dispatched creation uncertainty is retained.
- `namespace-host.ts` supplies a separate broker directory, registry, authenticated actor issuer, immutable genesis and writer controls for each provider repository ID. Requests carry `x-strata-repository`; an old tab cannot silently write to the new selection. Private drafts, request caches and author heads are never inferred from a remote repository name.
- Owner login remains one hour absolute / fifteen minutes idle, with fresh confirmation for credential administration and namespace approval/revocation. Active project requests refresh idle time without extending the absolute deadline or fresh confirmation. Actor sessions remain finite and parent-bound. These are authentication lifetimes, not namespace grant expiry.
- API credentials remain server-side in the encrypted owner store. Credential rotation invalidates actors and write qualification. Git uses short-lived repository tokens issued per bounded operation; only known owned token IDs are cleaned up by the existing adapter.
- One namespace ledger reserves provider requests and bounded transfer before dispatch. Replay does not dispatch or refund. New project grants use that shared ledger; opening another repository cannot obtain a fresh allowance.

The root policy and private catalog are a **new lineage**, not a mutation or expiry extension of a managed-reader `SourcePolicy/1`, existing repository grant, original writer or prior accounting. The candidate [namespace mode operator](NAMESPACE_MODE_OPERATOR.md) preserves previous lineages and deducts cumulative predecessor/conformance spending from the new allowance. It restores only original host configuration on rollback and retains all private history and usage. It does not import or reset an existing writer.

Revocation publishes its flushed, exclusive tombstone before the catalog. An OS failure between those two synchronous publications leaves access refused on reads and restart; it requires operator reconciliation without removing the tombstone or resetting accounting. Successful revocation and its exact request replay survive restart normally.

## Actual provider boundary

The implementation follows the [Artifacts REST API](https://developers.cloudflare.com/artifacts/api/rest-api/) and [authentication guide](https://developers.cloudflare.com/artifacts/guides/authentication/).

- The REST credential needs the actual appropriate Artifacts Read/Edit permissions. Saving a token or viewing metadata does not verify its account/resource permissions. The product restricts its own requests to the sealed account/namespace; it does not claim Cloudflare supports namespace-specific API-token resource restrictions.
- Repository/token operations are name-addressed. Metadata ID checks detect replacements but do not supply an atomic expected-ID condition on mint/write. Activation therefore requires explicit acceptance of `development-name-addressed` and no namespace/repository deletion, recreation or rebinding during writes or reconciliation. This is not a production immutable-ID guarantee.
- Repository creation can auto-create a missing namespace upstream. Studio first GETs the exact namespace and refuses an absent or invalid response. It never POSTs a namespace. A deletion between GET and POST is not proven impossible; the development operator rule remains necessary.
- Create returns a plaintext automatic token with an encoded expiry, but no owned token ID or TTL input. Studio never uses or persists that secret, never guesses its ID and never lists other tokens to infer ownership. Policy must explicitly choose `discard-secret-and-allow-provider-expiry` and an `automatic_token_max_lifetime_seconds` bound (60 seconds to 366 days). A missing, malformed or longer expiry leaves creation uncertain. **Discarding is not revocation.** Actual provider behavior and the accepted bound must be qualified before live creation.
- Lost create responses may mean a repository and automatic token already exist. The original request remains uncertain; the same name cannot be blindly retried, adopted or deleted. Outcome inspection is local and discovery is a separate bounded read. Operator reconciliation of incomplete projects is not automated in this slice.
- Unknown repositories appear as **Import required**. Only complete projects registered on this installation can open for writing. Remote blobs alone do not contain the canonical private writer registry, actor context or idempotency history. A separately qualified complete import/synchronization protocol remains future work.

## Operator composition

The existing hosted launcher accepts an optional `namespace` object containing canonical absolute `policy_file`, `catalog_directory` and `projects_directory` paths. It requires `browser_owner` and refuses mixing namespace mode with workspace, managed-source or legacy-reader modes. Production browser-owner hosting retains the Linux protected-file checks. All control, credential, catalog and project paths must be disjoint.

The policy schema has no implicit account, namespace, identity, spend allowance or token-expiry choice. `initialNamespaceFiles(policy)` is a pure provisioning helper for a **new** lineage: it returns unapproved state and zero initial usage. A trusted operator must install the approved policy and initial files with the existing protected-file procedures. It is never called by service startup. Do not use it to replace an existing accounting history.

`first_project` is an optional strict policy field, included in the namespace digest and displayed approval scope. It requires a finite template, parameters, explicit single-human role choice and an absolute authority expiry. The `approve` action must additionally carry its exact `project_authority_sha256`; the host cannot silently promote existing owner mappings. It applies only to newly initialized projects and is sealed into their genesis. Imported repositories retain their separate draft-only admission.

`runNamespaceStudio` accepts optional `OwnerAgentSettings` and returns a secret-free `selectedSource.current()` port with `{selection_id, epoch, binding: {project_id, model_version, repository_id}, valid_until: null}`. Null describes durable source consent only. Selection, pause/revoke and credential invalidation call `settings.changed()` synchronously. A composition layer can use a deferred trusted local source callback to resolve construction order. Each agent connection must retain its own exactly bound per-repository consent store; this host never retargets agent consent or installs a provider auth port.

## Verification

After building, run `node --import ./tests/no-external-fetch.mjs --test --test-concurrency=1 dist/tests/studio-namespace.test.js`. The fixture uses real owner/actor HTTP, broker/engine persistence, REST adapter and Git pack verification with synthetic credentials. Cases cover two-project draft isolation and restart, replay accounting, missing namespace, lost create response, authentication/CSRF/scope, writer lease, pause during dispatch, credential rotation, revocation rollback, repository ID replacement, conflicting creation IDs, active idle renewal and absolute login expiry.

`tests/studio-namespace-browser.mjs` uses installed Playwright/Edge, `STRATA_EXPLORER_PLAYWRIGHT_MODULE`, and optional `STRATA_NAMESPACE_EVIDENCE` output directory. Browser traffic is intercepted to loopback; external requests are blocked. It exercises Settings, creation, persisted draft save, discovery, switching, restart/sign-in, desktop/mobile layout and keyboard dismissal. Screenshots and run receipts belong outside tracked documentation.

`tests/studio-namespace-control.test.ts` covers interrupted approval at admission and after flushed staging (logout, absolute/freshness expiry and control invalidation), legitimately committed consent/replay after logout, full-history pause/revoke/replay/restart, retained accounting, reserved-entry validation and failure between tombstone and catalog publication. It uses zero provider calls.

## Required action-time activation approval

Local implementation/testing is not approval for live credential entry, persistent access expansion, provider mutation or deployment. The owner must approve a concrete reviewed package containing:

> Activate commit **[exact reviewed commit]** on **[exact host/origin]**, with new namespace lineage **[ID and policy digest]**, for installation/owner **[IDs]**, Cloudflare account **[account ID]**, existing namespace **[exact name]**, and author **[principal/account IDs]**. Permit discover, create, read and draft operations until revoked within **[request/byte/operation/project bounds]**. Use **[identified protected credential generation and verified permissions]**. I accept the documented development name-addressing boundary and no-delete/recreate/rebind rule. For repository creation, I accept discarding the unused automatic token and allowing verified provider expiry no later than **[explicit maximum]**; this does not claim token revocation. Approve **[exact live conformance actions and repository names]** and **[exact separately reviewed host publication/configuration transition]**, preserving all prior data, private writer history and spending. Release roles, agent-provider activation and other scopes are excluded unless separately specified.

The package must resolve actual API permissions, namespace admission, automatic-token expiry, Linux custody and lost-response reconciliation before enabling live creation. No blocked recovery or unrelated candidate is part of this workflow.

When enabling `first_project`, the action-time package must separately identify its exact authority digest, collection parameters, named person, Block scopes, approval kinds, role expiry, finite checker and fixed output slots. The owner must explicitly approve that single-person workflow; the namespace-only approval statement above excludes it. The browser then confirms the displayed first-project digest through the authenticated approval operation.

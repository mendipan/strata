# Browser-first Studio owner setup

Design handoff against accepted `1f254140fa88c8b9eb001b67f328a96698205e7d`. This document proposes implementation; it changes no runtime, host configuration, account, credential, source grant or deployment. Astra High reviewed the owner-binding and UI decisions. Product examples and tests must remain generic; host-specific observations and approvals stay outside Git.

## Decision and verified feasibility

Use **one browser request approved through the existing authenticated host-management path**, followed by owner-chosen sign-in and provider-token entry on the HTTPS site. A public request code identifies the browser request; it is not a claim credential. The operator approves only the exact code the human owner supplies from their own page through the established trusted conversation. Never approve the first/latest request, one obtained from logs, or a request suggested by untrusted content.

Read-only hosting inspection confirmed an existing authenticated administrative route to the host/container. Current ingress establishes TLS, a pinned proxy and exact Host/Origin; it establishes no browser-owner identity. No existing upstream owner-authentication integration or browser-approval endpoint was found. The deployed setup was verified unconfigured: known legacy key files, credential-store files and bootstrap markers were absent. Recheck this nonsecret state before implementation activation; these observations are not permission to overwrite later state.

The owner performs no terminal commands and shares no password, provider token or encryption key with an agent. The only out-of-band step is copying a nonsecret request code into the existing trusted conversation. An authenticated operator then performs a bounded local management action. An entirely self-approving public website cannot establish rightful ownership with the current infrastructure. Passkeys would still need initial owner binding; upstream identity would require a new, separately verified identity integration. Neither is needed for this slice.

Recommended storage is an independent random encryption key generated on the server during approved setup, in a separate protected directory from ciphertext. The owner explicitly accepts the host-bound storage model on the setup page. Host administrators and backups containing both key and ciphertext can recover the token; separate directories do not provide independent-device or TPM protection.

## Owner-binding protocol

### Protected control record

Provision one fixed, bounded, root-controlled JSON control file outside every service-writable directory. The service may read it but cannot replace it or any ancestor. Direct read-only access avoids restarting in the middle of approval; `LoadCredential` does not provide runtime updates.

Proposed `strata-studio-bootstrap-control/1` fields: `installation_id`, random `enrollment_epoch`, `control_generation`, `origin`, `purpose` (`enroll-owner`, narrowly scoped `resume-owner-enrollment`, or `recover-owner-password`), `expected_owner_generation`, `issued_at`, `expires_at`, and `state` (`armed|approved|closed`). An approved record additionally binds a random `approval_id`, `pending_id`, `browser_cookie_sha256`, fixed `scope`, and the pending request's expiry. Resume also binds the existing transaction/initialization ID and manifest digest; password recovery binds the existing opaque owner ID and authentication generation. The independently retained `owner_binding` is initially absent and is sealed after the first durable enrollment; it binds installation, initialization ID, owner ID, key ID and immutable initial-manifest digest. No usernames, passwords, cookies, keys, provider values or free-form commands belong here.

Publish control transitions by exclusive temporary creation, fsync, atomic replacement and directory sync. Strictly check format, ownership, modes, regular-file status, ancestors, size (4 KiB maximum), exact configured origin and all generation/binding fields. The filename is configuration, never browser input. Root-owned 0755 ancestors and a 0644 control file are acceptable for this deliberately nonsecret record if the host policy permits public metadata; service write access is forbidden. A more restrictive pre-existing read ACL is also valid. Do not hard-code a transient DynamicUser UID or introduce a broad supplementary group merely to make this work.

Root control is the independent enrollment anchor: `armed -> approved` binds one request and consumes the current arm operation before account creation. The operator cannot approve a second request in that epoch. Expiry, lost cookies or abandoned approval require an explicit new operator-controlled epoch; neither HTTP nor missing app files rearms setup. A new epoch invalidates old pending requests and frees their capacity. The small anonymous pool bounds resource use, not availability against sustained denial-of-service. Restoring a whole-host snapshot is not rollback-resistant: operator reconciliation must invalidate old epochs before reopening recovery.

### Browser request and approval

1. While explicitly armed, the page offers **Start setup**. A same-origin JSON POST with pre-session CSRF creates a pending request, a random 256-bit `__Host-strata_setup` cookie and an independent public 128-bit request code. Cookie flags: Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. Persist only its digest, not the cookie. Return the public code, exact origin, purpose, expiry and memory-only CSRF.
2. Permit at most 8 pending requests and 5 new requests/minute globally; reaching a bound returns a clear retry response and grants nobody authority. Pending lifetime is 15 minutes; polling does not extend it. Root arming is bounded to 30 minutes. A first visitor cannot reserve the only owner slot. A browser refresh resumes only its own cookie-bound request; public codes cannot query, redeem or cancel requests.
3. The owner copies the code from their own HTTPS page into the trusted conversation. The operator reads only sanitized pending metadata, matches the supplied code plus installation/origin/purpose, and atomically approves that exact tuple using the existing authenticated host-control route. No public HTTP approval route exists. Approval expires within 10 minutes and never later than the pending request/root arm expiry.
4. Only the original cookie-bound browser observes approval and receives the sign-in form. Approval alone creates no owner, provider access, persistent session or project grant. Poll every 3 seconds while visible; pause in background and stop on expiry/cancel/complete.
5. The final browser POST rechecks the protected control record, request/cookie/CSRF binding, expiry and expected generation under the setup transaction lock. One successful activation consumes the approval ID and closes all other pending requests, but remains **activated-awaiting-seal** with no owner authority.
6. The original bounded operator approval operation observes only the sanitized durable enrollment receipt and atomically seals `owner_binding` against the immutable initial manifest. It runs only until the original expiry, then exits; there is no recurring task or new daemon. If interrupted/expired, an authenticated operator must deliberately reconcile the exact installation/approval/transaction/manifest before sealing. The page shows **Finishing setup**, then **Account created; sign in**. The setup cookie never becomes a management session through GET polling. Root retains the seal across later recovery epochs; app-file loss after sealing cannot make fresh enrollment valid.

The local operator utility is implementation code used by the authenticated administrator, not a user-facing terminal runbook. It accepts only fixed operations and nonsecret identifiers: inspect pending, arm an explicitly approved epoch, approve/seal an exact pending tuple, reconcile an exact incomplete transaction, and close. It must refuse unknown paths/commands, stale state and automatic selection of a pending request. Pending records are untrusted data: bounded fixed-path reads, no symlink traversal, strict fields and no execution/interpolation. Every output is sanitized metadata. Reconciliation never deletes or resets an active/sealed owner; unexplained artifacts are preserved for explicitly approved repair.

## Owner identity and session

Add a single installation-owner identity with a generated opaque ID and chosen sign-in name (3-32 ASCII letters, digits, dot, underscore or hyphen; canonical lowercase shown to the owner). This is installation credential management, not a Strata authoring principal, verified email identity, or project authority.

Use a separately versioned salted password verifier. Recommended initial Node 22 implementation: asynchronous scrypt, `N=32768, r=8, p=3`, random salt of at least 16 bytes, 32-byte result and explicit 64 MiB KDF memory cap. Admit one KDF at a time, with a bounded queue of two; reject excess work before expensive hashing. Benchmark under the deployed service limits before release; do not silently reduce parameters or broaden resource limits. These parameters follow an [OWASP scrypt memory/CPU option](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt); [Node documents asynchronous scrypt and its memory limit](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

Accept 15-128 Unicode code points after consistent NFC normalization, at most 512 UTF-8 bytes, without silent truncation or composition rules. Allow paste and password managers; reject control characters and a bounded local list of common/context-specific passwords. Do not query an external breach service. Confirm-password is a client-side equality check; transmit only one password. The [NIST password guidance](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) supports long passwords, normalization and blocklist checks; this design makes no NIST assurance-level certification claim.

Owner sessions use a distinct `__Host-strata_owner` cookie, random 256-bit ID, 15-minute idle / 1-hour absolute expiry and at most 4 concurrent sessions. Restart clears sessions. Every action rechecks current owner ID/authentication generation, configured installation and fixed allowed scope. A generation change, password recovery or sign-out revokes the applicable sessions. Login is bounded to 5 failures/minute globally with persisted capped backoff; no permanent lockout, guessed-IP identity or forwarded-client rate-limit key. Invalid username and password return the same error and do equivalent bounded verification work.

Owner session scopes are exactly existing read UI and credential status/save/remove/test. Credential mutations and tests require authentication within the last 5 minutes; otherwise show a password reauthentication dialog and then require an explicit retry. Reauthentication rotates session/CSRF and invalidates the old session ID. The normal sign-in after sealed setup counts as fresh authentication. Shared reader and named author cookies confer none of these management rights; owner cookies confer no authoring, approval, Release or source-grant management rights.

## Persistence and recovery

Explicit browser-owner configuration supplies a read-only `control_file` and canonical private `state_directory` / `key_directory`. They must be within operator-approved storage, disjoint from ciphertext, with no symlinks and appropriate ownership/permissions. Use private directories 0700 and secret files 0600. The running service writes only these approved state paths. No `/etc` writes, UID guessing, environment-key fallback, arbitrary path submission or automatic permissions repair.

During approved **Create owner account**:

1. Acquire an exclusive setup lock and revalidate the current protected approval and uninitialized state. Existing legacy/owner artifacts or unexplained partial files block fresh enrollment.
2. Generate the independent 32-byte store key with the server CSPRNG. Create a unique transaction generation containing the salted owner verifier, an explicitly empty encrypted credential store, a sanitized transaction manifest and the key in its separate approved key directory. Use exclusive creates; never overwrite an existing key or owner generation.
3. Fsync and validate every staged artifact. The manifest binds installation, epoch, approval ID, expected/new generations, account ID, key ID and exact artifact identities. Passwords and raw key bytes never enter the manifest or logs. Do not persist a fast password/request-payload digest that weakens the slow verifier.
4. Revalidate approval immediately before atomically publishing a small activation pointer to the prepared generation. This is the application commit point; owner/store initialization and consumed approval become durable together, but access remains unavailable until the independent root seal matches. Seal the immutable initial manifest, never the mutable auth pointer or a forever-pinned ciphertext digest. Mutable encrypted-store revisions subsequently use the existing store CAS.
5. Return a nonsecret operation outcome (`202` while awaiting seal); never retain the password while waiting for the operator. After sealing, offer ordinary password sign-in, which creates the distinct owner session. A failure to deliver the response never rolls back a committed account. The owner does not need another terminal or approval action to finish the original still-valid bounded approval operation.

Durable app states are `uninitialized`, `pending`, `approved`, `preparing`, `activated-awaiting-seal`, `active`, and `recovery-required`; pending requests may also expire/cancel. Root control must independently authorize entry to the first three states. Missing or invalid established activation, verifier, key, ciphertext, generation or transaction artifacts never reopens enrollment, generates a replacement key or reports an empty store. Current store behavior on a missing file must be overridden for initialized owner mode. An approved but unsealed root record does not prove that application commit never happened: loss of preparation/activation evidence in that state requires operator reconciliation, not repeat initialization. Only a matched independent seal permits normal owner access.

Crash tests determine recovery at each boundary. Before activation, the same approved browser can deliberately resume only its exact prepared transaction and artifact identities while authorization is valid. Re-entered username/policy must match; verify the re-entered password against the prepared slow verifier. Changed input returns conflict; do not replace staged credentials or regenerate the key. Incomplete/inconsistent preparation requires narrow operator reconciliation. Expired/lost-browser resumption needs a fresh bound request with `resume-owner-enrollment` purpose and the exact existing transaction; it is not a fresh account request. Do not auto-delete a lease by elapsed time alone. After activation, startup validates the generation and root seal before offering normal sign-in, even if the setup response was lost. Same-cookie read-only outcome lookup reports **Account created; sign in** only after sealing; it does not mint a manager session or repeat setup. Secrets are re-entered for a deliberate pre-commit retry, never saved in browser storage. An operation UUID identifies outcomes but is not authentication.

Normal password change first verifies the current password through reauthentication, then submits only the new password within 60 seconds using that rotated session. It atomically rotates the verifier/authentication generation and preserves the independent store key/token. This avoids putting two maximum-length passwords into the 1 KiB request. Forgotten-password recovery repeats the bound-browser operator approval with a distinct recovery purpose and exact existing generation; it never becomes fresh enrollment. Missing encryption material is a separate blocked recovery state. Discarding unusable ciphertext and re-entering a provider token needs a separately described owner action; password recovery must not silently do this. No key export/download, plaintext retrieval or recovery-question flow is included.

Authentication rotation/recovery changes only auth state and retains the original initialization, key and live credential-store references; never copy an earlier ciphertext snapshot or initialize an empty store. Use one installation mutation coordinator: acquire owner-generation lock before credential-store lock for mutations that need both; never reverse this order. Credential actions reread authority within that serialization. Rotation therefore either follows a completed token update or revokes the queued action before it changes storage. Provider tests remain bounded and no lock is held while waiting for browser input or operator approval.

Owner acknowledgement shown before the final setup action:

> Studio stores your API token encrypted on this host. Its encryption key is also protected on this host. A host administrator or a backup containing both can access the token. Losing the key means entering the token again.

## Browser/API contract

All routes use the existing verified HTTPS/proxy boundary, no query parameters, no-store, strict JSON and positive field schemas. Every POST requires exact Origin and current session/pre-session CSRF; GETs accept no body. Keep the existing 1 KiB request limit and test maximum valid serialized requests through the proxy. Do not send password confirmation or provider token in the enrollment request.

| Route | Purpose and authority |
| --- | --- |
| `GET /studio/setup` | Sanitized availability/current cookie-bound request state; may establish a bounded pre-session CSRF cookie. No list of requests, account name, key metadata or arbitrary request lookup. |
| `POST /studio/setup/request` | `{request_id, expected_generation}`; create/reuse this browser's pending request while root control is armed. |
| `POST /studio/setup/cancel` | `{request_id, expected_generation}`; cancel only this browser's pending request. Never undo an active account. |
| `POST /studio/setup/complete` | `{request_id, expected_generation, username, password, key_storage_policy:'host-bound'}`; only exact approved browser; durably activate one owner/store generation, then await independent seal. |
| `GET /studio/setup/outcome` | Same setup cookie; sanitized result of this browser's last commit attempt, including unknown/recovery-required. No mutation or session upgrade. |
| `GET /studio/owner/session` | Separate owner-auth state/CSRF/fresh-auth expiry; no secret verifier or supplied password. |
| `POST /studio/owner/login` | `{username,password}` with pre-session CSRF; create/rotate owner session. |
| `POST /studio/owner/reauth` | `{password}` with owner CSRF; rotate session and freshness after current generation checks. |
| `POST /studio/owner/logout` | Empty JSON; revoke session, clear owner cookie and client secret fields. |
| `POST /studio/owner/password` | `{request_id, expected_generation, new_password}` within 60 seconds of password reauthentication; no credential-store reset. Recovery uses a separately armed setup purpose/schema, never an implicit switch in the enrollment body. |
| `GET/POST /studio/v1/owner/credentials` | New owner-only wrapper. Reuse masked status/CAS/UUID/store action semantics; body has no `owner_authorization` or identity claims. Recheck fresh owner authority for replay and inside serialized action. |

The new credential wrapper returns a separately versioned `strata-studio-owner-credentials/1` projection: preserve masked store fields/revision/capabilities, with `management.authorization:'owner-session'` and `reauth_required`. Do not label owner-session actions as the existing `owner-key-per-action` contract. Both admission paths call the same server-only admitted store action; client input cannot construct the admitted context. Read projection accepts the owner cookie through a dedicated HostedReadAccess adapter, while the actor command branch remains absent. Async owner-state checks must be awaited by host routing; no unchecked Promise or silent legacy fallback.

Recovery completion must have its own discriminated payload, expected owner/authentication generation and fixed purpose, and may reuse the common transaction machinery. Existing `/studio/login`, shared-reader sessions and `/studio/v1/credentials` retain legacy behavior. Explicit browser-owner mode is mutually exclusive with legacy sign-in/manager-file bootstrap configuration. Ambiguous mixed configuration refuses startup. Existing project connection configuration may be reused only under its separate authorization.

Errors are sanitized and stable: `SETUP_DISABLED`, `SETUP_NOT_APPROVED`, `SETUP_EXPIRED`, `SETUP_CHANGED`, `SETUP_ALREADY_COMPLETE`, `SETUP_RECOVERY_REQUIRED`, `SETUP_BUSY`, `OWNER_SESSION_REQUIRED`, `OWNER_REAUTH_REQUIRED`, `LOGIN_LIMIT`, plus existing input/origin/storage errors. No paths, hashes, key material or internal exceptions in responses. Status distinguishes **sign-in created**, **token saved**, **connection not configured**, **grant expired**, and **read test passed**.

## UI sequence and copy

Use the current centered welcome card and subsequent Settings layout: paper background, warm cream cards, rust accents, existing typography, dark primary action, visible focus ring and 44px controls. One primary action per step; 375px width must fit without horizontal scrolling.

1. **Set up your Studio.** Explain the one-time browser confirmation. **Start setup** appears only when explicitly armed. Disabled state says **Owner verification has not been enabled for this installation** and offers a nonsecret status copy, not terminal instructions.
2. **Confirm this browser.** Display exact site origin, public code, purpose and expiry. **Copy request code** gives visible **Copied** feedback. Explain sharing it in the existing trusted setup conversation. **Cancel setup** is available; no secret inputs yet. Expiry shows an actionable new-request path subject to the current root epoch.
3. **Create your sign-in.** Sign-in name, password and confirmation with visible labels, password-manager autocomplete, paste and individually labelled show/hide buttons. Explain length requirements inline; focus the first invalid field and announce errors. Show the host-bound storage acknowledgement with an explicit acceptance control. **Create owner account** disables during dispatch and clears password fields before dispatch. An uncertain response offers **Check setup outcome**, not an automatic second commit.
4. **Account created; sign in.** During the bounded operator seal show **Finishing setup** with truthful status and no secret fields. Once sealed, use normal sign-in with the chosen name/password and then open provider Settings. A lost response or restart uses the same ordinary sign-in path; no second owner is created.
5. **Save your Artifacts token.** Mask input by default; **Show token** reveals only the current draft, never a saved value. **Clear field** clears immediately. **Save token** stores it and announces **Token saved on this server** with time/status. **Skip for now** preserves the completed owner account. Saved token is not automatically a connection test.
6. **Connect when authorized.** Display only configured safe connection metadata and exact missing prerequisites. **Test connection** runs only when a trusted registry, repository binding and valid read grant exist. No provider dispatch occurs on enrollment, login, save, status polling or restart. Saving does not issue a grant. Keep project connection/approval operations outside bootstrap.

After setup, normal sign-in uses the same password-manager-compatible form. Credential management no longer asks this owner for a separate long manager key. Expired management freshness opens a small labelled reauthentication dialog; Cancel preserves the nonsecret page state and restores focus. Replacement/removal of a stored token uses explicit confirmation; clearing an unsaved field is a separate action. Navigation/cancel/logout clears all draft secret values and returns them to masked mode. No application-managed localStorage, sessionStorage, IndexedDB, URLs, analytics, clipboard actions or log output contains secrets. A user-controlled password manager may save the chosen login; the application does not persist it in browser storage.

## Measurable acceptance gates

| Gate | Required evidence |
| --- | --- |
| Owner binding | Two concurrent browsers: first visitor and code-only caller gain no authority; only the human-selected, cookie-bound request can complete. Wrong cookie, duplicate cookies, stale epoch/generation, wrong origin/purpose, expired/canceled request and replayed approval all fail. At most one owner generation commits under concurrent completion. |
| Control boundary | HTTP cannot arm/approve/close, spawn commands, choose paths or write control files. Root-record/ancestor mode, owner, symlink, malformed/oversized/unknown-field and binding attacks fail. App-file deletion alone cannot rearm. Operator never selects latest pending automatically. |
| Web admission | Exact Host/proxy/Origin, Fetch Metadata, pre-session/session CSRF, method/content-type/query/body limits, cookie flags and no CORS remain enforced. All largest supported Unicode-password/token bodies pass the real 1 KiB proxy boundary; oversized input is refused before KDF/storage. |
| Authentication | Wrong credentials, queue/attempt bounds, NFC/count/byte limits, blocklist, password-manager paste and timing-neutral failures. Rotation/recovery/logout/expiry/restart revoke old owner sessions. KDF runs asynchronously, one at a time, inside existing resource limits without starving static/status responses. |
| Least privilege | Shared reader, named author and pre-setup cookies cannot manage credentials. Owner cannot call authoring/approval/Release or create/read-renew a project grant. Unknown identity/policy/role fields are rejected. Credential replay repeats authorization; revocation while queued is refused before write/provider dispatch. |
| Durability | Inject failure before/after each file create, fsync, rename, activation and root seal; restart from every point. No authority before matching seal, half-active account, regenerated established key, overwritten prior state or missing-ciphertext-as-empty result. Same-request lost-response outcome is accurate and never executes twice. Changed prepared password conflicts under slow-verifier checking. Delete established app artifacts while retaining root seal: access and enrollment both refuse. Concurrent processes/leases remain serialized; ambiguous stale leases require deliberate reconciliation. |
| Recovery | Password recovery preserves key and ciphertext, rotates authentication generation, and rejects another request/owner/generation. Missing key/ciphertext, unknown legacy partial state, restored old epoch or invalid activation blocks rather than reenrolls. No secret recovery/export response. |
| Secret containment | Synthetic sentinels absent from all responses except intentional current-input reveal, server/proxy logs, URLs, copied public code, browser storage, saved screenshots, errors and operator receipts. Password/hash/key are absent from transaction metadata; no fast password digest side channel. Draft values clear on dispatch/cancel/navigation/logout. |
| UI | Keyboard-only start/approval/create/save/sign-out, labelled show/hide state, copy feedback, error focus, cancellation/focus restoration, repeated click, refresh, browser back, expiry and lost network response. Desktop and 375px mobile fit current style with no horizontal overflow. Clear-field and remove-stored-token are distinct. |
| Provider separation | Mock provider count remains zero for setup/login/save/status/restart/denied operations. Explicit test needs saved token plus separately valid binding/grant and uses existing exact deadline/budget. Expired or absent grant cannot be repaired by owner sign-in. |
| Compatibility | Existing local preview, shared-reader mode, legacy per-action manager mode, named actor/CLI authority, credential encryption/CAS and source gates pass unchanged. Mixed legacy/new config refuses rather than selecting a fallback. |

The already approved external read connection remains an external operator action after secure setup is ready. Its exact repository, fixed registry and budget/expiry are not product fixtures and are not broadened or started by this design. Its useful lifetime must begin only at explicit activation, not while enrollment is unavailable.

## Required handoff/owner actions

No open choice blocks writing the generic implementation. Recommended defaults are the bound-request operator approval, password sign-in, one-hour owner sessions and explicitly acknowledged host-bound key storage. Before live activation, present the concrete reviewed host-mode/control-path changes for approval. During use, the owner supplies the public request code through the existing trusted conversation, approves that exact browser binding, then confirms account/key creation and types all secrets on the HTTPS page. If the owner rejects this verification step, the remaining alternative is a separately configured authenticated identity channel; do not substitute LAN membership or first arrival.

Stop after this architecture commit for the planned Sol 6.1 XHigh implementation handoff. This design does not authorize installation, arming, account creation, recovery, key generation, provider access, source-grant activation or deployment on a real host.

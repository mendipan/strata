# Namespace profile persistence

Namespace Profiles uses `BuildProfileService` inside the existing sole Node broker queue. Contracts, named profile revisions, archive records, and post-publication adoption bindings use the existing strict supporting schemas, immutable artifact locators, canonical registry publication, workspace commit lineage, audit, and original request receipts. There is no separate profile database or writer.

## Explicit mounting and authority

The sealed project manifest may include `profiles: { authority_ref: "ExactBaseline@1" }`. The exact baseline supplies the repository review authority; it is not a request field or an implicit current selection. Project policy accepts existing `/2` or explicitly authored `/4` records. Existing manifests remain unchanged, and project creation/import continues to create the existing `/2` authoring policy. Owner login supplies neither new grants nor contract reviews.

Activation requires separately reviewed manifest/catalog bindings and narrow policy `/4` operations with the exact immutable repository ID in `build_repository_ids`. The service does not upgrade existing manifests, policies, catalog hashes, credentials, or grants. Contract imports and adoption still need exact retained `build-contract-review` records. Reviews can be produced by a separately authenticated reviewer through the private transaction seam; the public HTTP envelope cannot select a callback or assert a review.

Profiles can be mounted without Local Build output. Capabilities report support per operation through `ProfilesBuildStudioPort.supports()`. Build operations/downloads remain unsupported on the profile-only port. Policy and repository authorization are independently rechecked by the service and broker, including cached replay and original supporting-receipt inspection.

## Shared Build dependency

- `namespaceProfileService(engine, scope, context, issuer)` returns the existing profile service bound to the admitted Engine, project, immutable repository ID, and current authenticated actor. Its retained-review resolver searches only exact published reviews in that repository. It implements the existing `BuildRepositoryLookup` interface (`compatibility`, `profile`). Construct it inside a transaction, and return snapshots/pins rather than retaining a mutable Engine between transactions.
- `startLocalBroker(..., { repository: { scope } })` mounts public profile commands. The returned `repositoryTransaction(context, command, input, options, work)` admits private short transactions on the same bounded queue. `work(engine, registry)` returns `{ data, write?, receipt? }`; an optional receipt has `{ key, digest, result }`. `options` has `key`, `expected_generation`, `expected_policy`, `dry_run`, and optional host-only `replay_authorize(engine, registry, cachedData)`. Private reads use `dry_run: true`; private writes use a stable original step key, distinct from a review/import step even for identical action/input. Callbacks are host-owned and never accepted from JSON.
- `NamespaceProfilesStudioAdapter(repository_id, call)` delegates existing profile commands to the broker. `call(command, input, options)` receives `idempotency_key`, `expected_generation`, `expected_policy`, and `dry_run`; it returns the existing broker envelope. A Build Studio port can delegate profile commands to this adapter and own Build commands separately.
- The Build coordinator runs outside the queue and uses several short transactions. Public Build dispatch, when configured through `repository.build`, is invoked outside the queue. Private attempt/registration/run writes consume the same registry publication and workspace guards. Public `build.reconcile` refuses; stopped-host recovery is separately configured.

Workspace admission requires every supporting and Build attempt record to name the grant's exact project and immutable repository ID. This applies to imported history, startup validation, and prepared writes before provider staging. Importing profiles authored for another repository requires a separately designed migration; changing their IDs would rewrite immutable history and is refused.

The exact verified host artifact cache is retained state, not a second authority. Restart validates it against canonical namespace locators and workspace commit lineage. Missing/tampered indexed cache refuses with `STORE_UNAVAILABLE`; startup does not fetch or repair it outside an admitted provider operation.

Private receipts retain optional host-owned `repository_step` metadata in the existing request registry. It binds project, repository, actor, command, exact input, created references, and the original callback result independently of arbitrary nested response data. Public original-outcome reads check this scope before returning data. Exact private replay rechecks current command/repository/review/child authority and returns the original callback data without invoking `work`, staging, publishing, or extending its journal. Custom original receipts keep their existing result shape; subsequent updates preserve the initial private callback snapshot. Legacy request entries remain schema-compatible; their retained created refs also protect nested supporting outcomes.

Consumers with additional authority checks must repeat them in `replay_authorize`; this authorization hook executes no effects. Review consumers repeat current Release-review authority and exact retained review/subject pins. Build child consumers repeat current Build/recovery scope and original attempt/key visibility. A cached acceptance consumer must treat ownership as already claimed and read the latest retained run, rather than interpreting the original `created: true` snapshot as permission to allocate/export again. Legacy private entries without separate callback metadata retain the consumer's existing cache/revalidation path.

## Qualification

`tests/namespace-profiles.test.ts` exercises production `WorkspaceRuntime`, `NodeArtifactsAdapter`, Git pack staging, `ArtifactRegistryStore`, broker, profile service, and Studio command port against an injected synthetic provider and loopback HTTP. It covers immutable revision CAS, exact-key replay, cold restart, adoption/publication closure, stale input/policy/view refusal, secret-field refusal, current actor/repository boundaries, uncertain publication outcomes, no-effect dry runs, and missing-cache refusal.

These tests establish local synthetic behavior. They do not initialize live host custody, activate grants, contact a provider, deploy, or qualify a Windows/Debian service installation. Local Build output, finite runner configuration, and controlled recovery are owned by the separate Build adapter.

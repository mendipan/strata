**Recovery and version navigation plan — proposal, 2026-10-04.**

This document proposes product behavior and a bounded implementation sequence. The first slice (`context show/use` and `layer restore`) is now implemented locally; see [LOCAL_RECOVERY.md](LOCAL_RECOVERY.md). The separate bounded Node-only backup slice is also implemented; see [LOCAL_BACKUP.md](LOCAL_BACKUP.md). Other new commands below remain proposals, and this plan does not authorize their execution. It changes no semantic specification, current CLI, deployment, credentials or provider state.

**Recommendation.** Adopt explicit navigation, recoverable drafts, corrective changes with preserved history, and verifiable local recovery copies. Keep personal context, semantic baselines, shared release selection and deployed applications distinct. The first small implementation slice provides personal context and restoration of an owned Layer as a new draft revision. A separate Node-only backup/verification/isolated-restore slice should precede reliance on the prototype for irreplaceable intent. Remote mirrors, deployed rollback and destructive retention belong later.

**Grounding and current gaps.** This plan uses [STRATA_MODEL.md](../STRATA_MODEL.md), especially sections 2, 4, 5 and 7.4; [CLI_PLAN.md](CLI_PLAN.md), sections 3, 6, 10 and 12; and [IMPLEMENTED_CONTRACT.md](IMPLEMENTED_CONTRACT.md). Implementation inspected at `0618dd9e090f8ce88484563254f167ab2c6c8be9`: [CLI dispatch](../src/cli.ts), [Layer/release rules](../src/core.ts), [status/diff](../src/service.ts), [authorization](../src/security.ts) and [Node publication](../src/local-broker.ts). These files remain authoritative for what works today.

- Working commands include `status [--candidate C]`, `inspect TYPE [REF]`, `diff LEFT RIGHT`, `layer create/revise/publish`, `compose`, `materialize`, `validate`, `approve` and `release`. Snapshot diff accepts Releases/Compositions; Layer-to-Layer diff is absent.
- Each Layer has an owned head. A revision requires the current exact head and increments it. All stored revision contents are immutable; drafts remain private, while publication exposes an exact revision without selecting it.
- Every Composition pins its baseline and selections. No global HEAD or current-release pointer exists, and Release publication moves neither work nor a running application.
- The model allows reviewed movement to a different baseline, but the current implementation rejects a baseline change inside `layer revise`. Use a new Layer identity for that workflow; do not describe rebase as implemented.
- Personal context and same-Layer/same-baseline draft restoration are now implemented. Bounded Node-only backup, offline verification/inspection and inactive isolated restore now work. There are no discard, general revert, checkout, mirror, clone, fetch or sync commands. Provider adapter mocks are not remote recovery or mirror support. The local registry and artifact bytes are durable data; ordinary source Git history does not back up ignored `.strata/` state.

| Affordance | Adopt in Strata | Intentionally avoid |
| --- | --- | --- |
| HEAD-like navigation | A personal, explicit context referencing an exact Release or Composition; show its baseline and selected Layers. | A hidden moving default that silently determines writes, approval inputs or deployment. |
| Draft recovery | Preserve old revisions; recover desired content by appending a new owned draft. | Moving the Layer head backward, deleting revisions or turning published content private again. |
| Undo accepted intent | A new explicit corrective Layer with reviewed preconditions, impact and evidence. | Automatic inverse text patches, order-based winners or a label that conceals history rewriting. |
| Older versions | Inspect an exact Release, select it for separate work, or materialize it with a supported pinned profile. | Assuming older means currently safe, changing live traffic, or restoring application data as a side effect. |
| Partial undo | An explicit proposal addressing particular semantic items and their obligations. | Selecting half a Layer or automatically removing dependants and safety criteria. |
| Backup and mirroring | Verified immutable bytes plus a consistent publication checkpoint and complete referenced history. | A blind directory copy, deletion propagation, bidirectional semantic merging or credential replication. |

**Keep four kinds of state separate.**

| State | Meaning and proposed treatment |
| --- | --- |
| Personal context | A local navigation preference for one project, workspace and principal. It may change without changing intent. |
| Layer head / Composition baseline | A Layer head is authoring concurrency state. A Composition's baseline and selected revisions are immutable inputs. Neither is a project-wide current version. |
| Shared recommended Release | A possible future team channel pointing at an exact Release. Defer until the user chooses whether this is needed, who may move it and what promotion means. |
| Deployed realization | Exact executable artifacts running in an environment, with runtime configuration and data compatibility. Deployment and rollback are separate, currently absent capabilities. |

Do not add a sixth semantic object or change canonical hashes to implement personal navigation. Context is stored as small broker metadata outside semantic records, bound to the local workspace and server principal. Processes sharing both intentionally share a generation; other workspaces/principals remain independent. Proposed contents are the project/principal binding, exact target reference and fingerprint, and a monotonic context generation. Derive the displayed baseline and selections from the target; do not store independently editable copies that can disagree. A selected Release is the baseline for new work, even though that Release also records its own historical parent.

`context use` must resolve an exact locally available target under current read permissions, then compare-and-swap the expected context generation. It must not fetch, grant access, create a Composition or switch projects. A stale update leaves the context unchanged and returns the observed generation. Context may guide navigation and show suggested explicit commands; mutation commands in the first slice still require their existing exact inputs. Do not accept `latest`, `HEAD` or an alias in immutable recipes. Another agent's context remains independent.

**Command surface.** The first three rows and the separate Node-only backup rows are implemented and advertised in current help; abandonment remains deferred. Deferred names remain reversible interface recommendations.

| Proposal | Exact effect | Scope |
| --- | --- | --- |
| `context show` | Show the principal's selected exact target, derived baseline/selections and context generation. An unset context is explicit. | Implemented locally |
| `context use TARGET --expect-generation N` | Change only personal navigation after verifying the exact target and context generation. First selection uses generation zero. | Implemented locally |
| `layer restore CURRENT --from PRIOR` | Append the next private revision of the same owned Layer, copying the supported proposal content of an exact older revision on the same baseline. CURRENT is the required head precondition. | Implemented locally |
| `layer abandon CURRENT --expect-generation N` | Retire an owned unpublished draft from future publication while retaining every revision and a recovery receipt. Requires the lifecycle rules below first. | Deferred; not a cosmetic hide action |
| `backup create --out NEW_DIR --max-bytes N` | Export a bounded consistent local recovery set and manifest into a new directory, with an explicit export scope. | Implemented Node-only; see LOCAL_BACKUP.md |
| `backup inspect BUNDLE --expect-project ID [--ref EXACT_REF]` | Read-only summary or exact historical record data under the separate offline export entitlement. | Implemented Node-only; see LOCAL_BACKUP.md |
| `backup verify BUNDLE --expect-project ID [--expect-digest HASH]` | Check the manifest, hashes, closure, supported formats and completeness without activating any restored authority. | Implemented Node-only; see LOCAL_BACKUP.md |
| `backup restore BUNDLE --out NEW_DIR --expect-project ID --expect-digest HASH` | Verify, then restore into a separate inactive recovery directory; refuse overwrite and live activation. | Implemented Node-only; see LOCAL_BACKUP.md |

Retain the existing `inspect`, `diff`, `compose` and `materialize` names. A separate `checkout` alias adds little while there is no working-tree replacement. Do not introduce a general `reset` command with multiple destructive interpretations. Automatic `revert`, deployment `rollback`, project `mirror` and remote `sync` receive no executable spelling in this MVP.

**Workflow: stop or restart unpublished work.** Editing a proposal input file alone does not change Strata. Once a draft is stored, stopping work means leaving it unpublished and excluding it from new recipes; its recoverable record remains. Starting over with a different baseline or distinct task uses an explicitly authored new owned Layer through `layer create --file F`. This is already possible and does not cancel an in-flight author operation.

For an earlier version of the same Layer and baseline, proposed `layer restore L@7 --from L@3` creates `L@8`; it does not restore the head to 3. Check ownership, current task/Block grants, the source's exact contents, baseline and model compatibility before staging. Copy semantic proposal content, not publication flags, approvals, validation or a previous distillation-review acceptance. Review and publication of the new draft remain explicit. Restoring a supplied-proposal draft must meet the existing source-bound review rules again.

Record the old head, source reference/fingerprint, resulting revision, actor and operation ID in the existing audited publication mechanism. Do not insert an unsupported `restored_from` field into canonical Layer records or misuse the current source-distillation form of `derived_from`. Recovery provenance must survive export as audit/history metadata. If the source contains unsupported operations, or restoring it would exceed current assignment scope, fail instead of copying a subset silently.

True discard is a later, explicit lifecycle operation. Proposed `layer abandon` should require a current unpublished head, owner permission and a lifecycle generation. It preserves the head/history, returns a durable recovery reference and retires all still-unpublished revisions up to that head from subsequent publication. Previously published revisions remain valid and selectable. Recovery then creates a new revision; it never reactivates an old publication capability.

Before offering abandonment, make revise, restore, abandon and publish participate in the same lifecycle generation check at commit. A pending publish prepared before abandonment must fail if abandonment wins; if publication wins first, abandonment must report that the revision is published. Returning to a superficially identical state must not make an old request valid again. This requires changes to existing operations and both brokers, so it is deliberately outside the first slice. Until then, do not call hiding a draft 'discard' or promise that it cancels other actors.

**Workflow: revisit a known Release.** With illustrative Releases `R1` (600-second hold) and `R2` (900-second hold), existing `inspect release R1` and `diff R1 R2` show the historical state. An explicit new Composition recipe based on `R1`, with no selected Layers, retains the 600-second rule. Existing `materialize R1 --profile booking-node/1 --out .strata/revisit-r1` can generate it when that profile supports the snapshot and the output directory is new/empty. Real commands must use the actual returned immutable references.

Choosing R1 leaves R2, its provenance and all prior candidates intact. It neither undoes R2 nor moves a deployed application. A proposal prepared for R2 cannot be silently inserted into the R1 recipe; author a compatible new Layer with reviewed preconditions. Context selection needs read access; materialization additionally needs the configured preparer operation grant.

A historical Release's validation describes the exact candidate, profile, output bytes and checks it recorded. Inspecting it does not require rerunning tests. Rebuilding with different profile/template/toolchain inputs requires new realization evidence; old evidence cannot be relabeled for the new output. Even an identical retained realization's historical evidence does not establish compatibility with today's deployment environment or data. The first slice provides historical navigation and previews, not a universal 'known good now' assertion.

**Workflow: undo accepted intent and review partial undo.** To continue from R2 while restoring a 600-second hold, an owner creates a new corrective Layer based on R2, explicitly expecting 900 and proposing 600 with consistent statements/criteria. The ordinary publish, compose, materialize, validate, approve and release sequence can produce R3. R3 is a new result with its own lineage; R1 and R2 stay unchanged. There is no automatic inverse operation in this proposal's first slice.

Before accepting a partial correction, compare exact structured items and review their affected requirements, acceptance criteria, relationships, contracts, consumers and declared assumptions. For example, a reminder that needs a 900-second hold may become invalid when the hold returns to 600. The correction must address the affected behavior through owned proposals and normal selection, or remain blocked. Do not silently broaden the writer's task scope, drop a dependant, loosen an invariant or transfer ownership.

Current compatibility checks are deliberately narrow; a graph walk cannot prove arbitrary prose compatibility. Unknown required checks or interactions remain blockers. Show the changed and affected items, retained obligations, unsupported actions and required authorities before publication. An item changed again since the chosen historical value requires deliberate author input; do not overwrite it because an old inverse looks plausible.

Layer-added acceptance inherited by a Release stays active after the original Layer is omitted. `remove_item`, Block deletion and restoration of deleted IDs are outside the current implementation; a recovery request requiring them must report the precise unsupported portion rather than claim a complete undo. Changing selections produces a new Composition and candidate fingerprint. Changed considered sets invalidate bound Resolutions, and changed candidates require fresh matching evidence and endorsements. No command may waive these gates under a recovery label.

**Workflow: rollback a running application.** Defer implementation. When deployments exist, rollback must choose an exact retained realization and an explicit environment, then check that environment's runtime configuration, data/schema compatibility, current security restrictions and deployment authority. It creates a new deployment event pointing at older executable bytes. It does not rewrite a Release, replace personal context or reverse database migrations. Irreversible data changes can block executable rollback and require a separately approved recovery procedure.

The user must decide deployment ownership, environments and data-recovery expectations before this becomes a product feature. The current local booking profile and semantic release approval are not evidence of a general deployment rollback capability.

**Concurrency and permissions apply to every recovery path.**

- Layer restoration compares the current exact head/fingerprint at the publication boundary and rechecks the current principal, policy and Layer/Block grants. A source read or a long preparation step grants no lasting write permission. Failed comparisons leave the publication index unchanged; any staged orphan bytes are not a successful revision.
- Reuse the existing principal/project/operation/input idempotency contract. A lost response followed by the identical authorized request returns the same new revision; it must not create another revision or rewind the head. Current authorization is checked before returning cached mutation results.
- Revisions and published flags cannot be reconstructed by trusting an input file's owner label. Publishing one's own draft does not confer composition-selection, scope, guardian, release or backup-export authority.
- Personal context needs current read permission and its own generation. It cannot grant access to a private peer draft, another project or a provider account. Keep per-agent contexts independent.
- Keep the existing nonempty-output and safe-path rules. Recovery never overwrites a realization, edits another author's Layer, deletes semantic history or uses a force flag to bypass a stale-state error.
- Current fixtures demonstrate broker-level isolation only. Do not promote recovery receipts or local audits into claims of production identity, cryptographic endorsement or protection against an administrator with filesystem access.

**Local backup and restore require a complete, consistent recovery set.** This is a separate bounded implementation slice, beginning with the Node broker. Use the current immutable artifact store and publication index rather than introduce a second history system. For the first exporter, require a quiesced Node broker and an explicit local operator export scope; report that requirement before doing any work. Do not stop another running broker automatically or describe copying live SDK SQLite files as a valid export. Online snapshots and an SDK exporter are deferred.

The manifest should identify the source project, model/storage formats, immutable checkpoint fingerprint, exported scope, root references, registry heads/publication metadata, file/hash/size inventory, and explicit exclusions. A full project recovery set includes all indexed published history and authorized private drafts, the transitive record/artifact closure, complete referenced realization bytes and manifests, evidence/approvals, and the historical commit/recovery receipts needed to explain publication. Rejected and superseded considered proposals are history too. Pin the exact implementation-profile assets or report that runnable reproduction is incomplete; a profile label alone is insufficient.

Full-project export includes other owners' private drafts and therefore needs an explicit operator/export entitlement. Ordinary project read access or Layer authorship must not imply it. The existing roles expose no such command or grant; its implementation is an explicit extension, not permission inherited from `fixture-reader`, bootstrap or a Cloudflare login. A smaller author recovery set may include published material and that author's visible drafts, but must be labeled partial and cannot advertise full project recovery. Do not truncate an unauthorized full export into a misleading 'complete' bundle.

Use an allowlisted inventory rather than archiving the entire workspace. Exclude OAuth/API/repo tokens, cookies, private keys, environment secret files, credential stores, active sessions, issuer assignments/delegation grants, provider account bindings, transient execution/cost grants and queued jobs. Do not copy a live runtime's membership or permission state into the destination. Application/customer runtime databases are a separate recovery scope, not implied by a semantic backup.

Preserve historical principal identifiers, ownership, authority manifests and approval references inside immutable semantic records: deleting those changes the history and breaks its hashes. Those historical identifiers are evidence about authorship, not usable login identities or grants. Sensitive business intent and private drafts retain their source confidentiality requirements. If export would expose a detected secret embedded in a canonical record, stop for an explicit handling decision; silently redacting that record cannot produce an identical verified backup.

Verification must check actual bytes against the pinned inventory, reference-to-content consistency, record/model versions, required dependencies/evidence/profile assets and bounded archive paths/sizes. Reject duplicate paths, escaping paths, links, conflicting immutable references, missing referenced bytes and partial checkpoints. Local hashes prove consistency against a trusted manifest/checkpoint; a self-consistent attacker-supplied bundle does not prove its authors or approvals are authentic. No missing remote object is fetched automatically. Unindexed staging orphans are excluded from the authoritative recovery set and reported separately.

Write the completion marker only after all declared bytes and closure checks pass. A size/time limit or interrupted export leaves an explicitly incomplete destination, never a successful backup. Copy verification is read-only. A restored directory must be new and separate from any existing project, and remain inactive until verification finishes. Failure cannot replace the destination's existing index or leave a partly activated project.

Restore preserves historical records and references without starting a broker, registering credentials, recreating accounts, issuing tokens, deploying, or granting historical principals current access. Do not activate restored request caches, pending jobs or authorization snapshots as live authority. Preserve relevant old operation receipts as history so a lost-response investigation remains possible. Resuming authoring in a recovered project needs a separate explicit local trust/configuration binding and renewed permission checks; a general cross-project migration or identity-remapping system is deferred.

**Mirroring is a later replication workflow.** A useful mirror would copy authorized immutable objects and append verified source checkpoints to an independent destination, resumably by content hash. It would preserve history, verify complete closure and expose source/checkpoint freshness. It must not propagate deletions by default, replace a destination's existing contradictory references, promote a source Release as the destination's current application, or manufacture ownership from copied identity labels. Keeping historical checkpoints makes recovery possible after an accidental source change. Retention, encryption, destination trust, offline writers and reconciliation need separate decisions; no bidirectional merge or conflict-resolution protocol is implied.

Remote fetch or mirror operations require explicit origin, destination, data scope, current authorization and a bounded provider cost/transfer/time grant at execution. Existing OAuth login supplies neither Strata authority nor spending permission. Restoring a backup cannot restore an expired cost grant. Expiry or exhausted limits must fail closed with precise partial-copy/cleanup results. No network calls, provider token creation, namespace creation, model calls or scheduled synchronization arise from navigation, semantic recovery or this document. Pending remote-smoke approval remains separate.

**Minimum scope and decisions.** Implement one slice at a time; this plan is not authorization to build all of them in one change.

| Priority | Deliverable and completion boundary |
| --- | --- |
| First slice, implemented locally | `context show/use` as personal navigation only, and same-Layer/same-baseline `layer restore` producing a new private revision. Reuse existing persistence, authorization, audit and publication rules. Keep all existing mutation targets explicit. Verified on both broker paths. No generic undo engine, Layer rebasing or discard lifecycle. |
| Independent local recovery slice, implemented | Node-only quiesced export, verification and isolated inactive restore with an explicit export entitlement and bounded manifest. Include a demonstrated restore drill. No live SDK database copying, remote copies or automatic trust reactivation. This is required before treating the prototype as the sole copy of valuable work. |
| Existing workflows to explain now | Exact inspect/diff, explicit old-baseline Composition, supported-profile materialization into a new directory, and manually authored corrective Layers through normal review/release. |
| Deferred | Logical abandonment and its publish/lifecycle races; shared release channels; general partial-undo assistance; broader semantic operations; online/SDK snapshots; production identity migration; remote mirror/sync; deployment/data rollback; retention/GC and hard deletion. |

The main gap is recovery usability and durable recovery packaging, not a need to replace immutable semantic history with Git branches. Preserve the current five semantic concepts and their authority rules.

| Decision type | Recommendation or question |
| --- | --- |
| Reversible implementation defaults | Exact-reference commands; personal display context; new revisions for restoration; empty output directories; retained history; full verification; local-only operation. Implement within an accepted slice without repeated product confirmation. |
| User product decision, deferred | Is there a shared recommended/current Release, and who can move it? Do not assume release publication means promotion. |
| User product decision, deferred | What are the deployment environments, rollback authority and data compatibility/recovery obligations? Keep executable rollback outside semantic recovery until defined. |
| User/operator scope decision before a backup run | Who may export every private draft, which destination may receive it, and what completeness is required? Never broaden author permissions implicitly. |
| User product decision before destructive or remote features | Retention/expiry and deletion rights, remote mirror destination/trust, encryption and data scope, offline collaboration expectations, and provider spending limits. Preserve data and stay local until these are decided. |

These questions do not block the small personal-context/owned-restore slice. Final command spelling and placement of nonsemantic local preferences are reversible defaults. A shared promotion policy, widening access to drafts, destroying history or authorizing remote transfer is not a spelling choice.

**Acceptance scenarios.** The first slice's relevant scenarios have passing local tests, documented in [LOCAL_RECOVERY.md](LOCAL_RECOVERY.md). Node backup/verification/inactive-restore scenarios now also pass in synthetic Temp workspaces; see [LOCAL_BACKUP.md](LOCAL_BACKUP.md). Other rows remain proposed checks for future slices. Each slice should execute only its relevant cases.

| Scenario | Required result |
| --- | --- |
| Select old Release R1 while R2 exists | Context changes at most; R2, records, evidence and deployment state are untouched. A new R1-based Composition retains R1's snapshot. |
| Use a context with an unavailable/private/foreign-project target | Fail without fetching, leaking private contents, switching project or inventing access. |
| Two sessions update the same personal context generation | Exactly one succeeds; the stale request reports the newer generation without overwriting it. Independent principals do not share a pointer. |
| Restore L@3 while current head is L@7 | Create only L@8 with the intended proposal content, private state and recovery audit. No older ref changes. |
| Another operation advances L@7 before restore commits | Fail the stale-head check; create no published revision and do not retry against the new head automatically. |
| Restore source belongs to a peer, has another baseline, or exceeds current Block assignment | Refuse. Explain the needed new owned proposal or authority; no partial copy and no automatic rebase. |
| Restoration response is lost; identical request is retried | Return the original authorized result once; no L@9 caused by the retry. Revoked permission still blocks a cached response. |
| Restore a published or distilled revision as a draft | Historical publication stays intact; new revision is unpublished and receives no copied approval/evidence/review authorization. |
| Future abandon races with publish or stale revise | One lifecycle generation wins atomically. No old unpublished revision is published after abandonment wins, and no previously published revision is erased. This must pass before enabling abandon. |
| Undo hold duration while retained reminder/criterion depends on the newer duration | Candidate stays blocked until explicit compatible intent and all required checks/endorsements exist. |
| Partial undo requires removal of inherited criteria or a deleted Block | Report the current unsupported operation; never omit the obligation or claim complete recovery. |
| Changed candidate reuses historical validation or an old guardian approval | Reject stale evidence/authority. History remains readable under current read access. |
| Materialize into existing output, or reuse old evidence for a changed profile/tree | Refuse overwrite or stale evidence; no inferred deployment safety. |
| Full backup encounters another owner's private draft without export entitlement | Fail the full export; an explicitly requested partial export must declare its omissions. |
| Backup has a missing object, conflicting ref, traversal/link, bad digest, unknown required format or incomplete checkpoint | Verification fails before activation, remote fetch or overwrite. Recomputed self-consistent hashes do not create identity trust. |
| Export is interrupted, exceeds limits, or the required broker quiescence is absent | No complete marker and no successful-backup claim; report the bounded partial destination. |
| Restore targets an occupied directory or contains credentials/active grants | Refuse overwrite; exclude/disallow active credentials and grants. Historical owner IDs remain inert and hash-preserved. |
| Restore a verified copy with historical author and operation receipts | Open only as inactive recovery data. Do not recreate login identities, replay queued work, bypass current authorization or reuse provider grants. |
| Node restore drill | Implemented through offline `backup inspect` without activation: inspect exact historical refs from the inactive copy, compare every retained artifact hash to the checkpoint and demonstrate that the original project was never changed. Separate trust reactivation and SDK recovery parity remain deferred. |

Implementation should report supported recovery scope and remaining limitations in help and results. A passed restore drill supports the tested local recovery contract; it does not establish production disaster recovery, replica consensus or safe rollback of arbitrary applications.
